# Competitor gap re-audit — 24 September 2026

## Scope and evidence

Target: English-medium schools in Bangladesh using Cambridge, Pearson Edexcel or IB, with the Bangladesh national curriculum as another configuration. This compares the current repository with **public vendor descriptions** from ManageBac+, Toddle, OpenApply, Fedena, DigiCampus BD, Eduman, PRS, Bidyaan and OpenEduCat. Vendor pages describe what the vendors claim; their private workflows were not tested. "Missing" means no corresponding model, route and user workflow was found in this repository. It does not mean every school needs that feature.

Older comparisons in `docs/MARKET_AND_COMPLIANCE_REVIEW.md` and `docs/digicampus-comparison.md` describe an earlier build. Do not use their old "missing" labels without checking current code.

## Already built — do not ask Claude to rebuild these

- School/class/exam grading rulebooks; Bangladesh, Cambridge, Edexcel, IB MYP and IB DP calculations; per-year class subject plans and per-student choices (`core/models.py`, `academics/models.py`, `examinations/rulebooks.py`, `examinations/subjects.py`).
- Co-teachers for a subject/section, validated assignments, class-teacher or section-teacher attendance policy, edit window and a daily summary showing who recorded attendance (`academics/models.py`, `attendance/services.py`, `attendance/views.py`).
- Weighted exam parts, comments, predicted grades, combined term results, versioned published cards, certificates, exam series and an official-result register (`examinations/`, `students/certificates.py`). Exam timetable clashes and official-result release dates are also handled (`examinations/clashes.py`, `examinations/official.py`).
- SSLCommerz-hosted online fee collection, including methods offered by that gateway, and a demo gateway; fees, double-entry accounts, payroll, SMS, a responsive family web portal and a partial Bangla interface (`fees/online.py`, `finance/`, `messaging/`, `core/portal_views.py`). This is **not** a separate direct bKash/Nagad integration or a native mobile app.

## Conditional programme gaps

1. The code has no explicit `Programme/Curriculum` record. A mixed-programme school currently creates distinct classes, and class grading can be overridden per exam. Add a programme/year structure **only if** a school needs the same named year level in multiple pathways or programme-wide planning/reporting. See `academics/models.py`, `core/models.py` and [ManageBac+ multi-curricula](https://www.managebac.com/multicurricula).
2. IB PYP narrative reports, IB CP workflows, Edexcel International A Level UMS/cash-in and moderation are explicitly deferred in `docs/IMPLEMENTATION_STAGES.md`. Confirm a pilot school uses each before building it. Toddle advertises [IB CP support](https://www.toddleapp.com/product/ib-cp/) and ManageBac+ advertises [programme-wide planning](https://www.managebac.com/multicurricula).
3. The Bangla interface covers navigation, family screens and report cards more than staff workflows. `docs/IMPLEMENTATION_STAGES.md` defers teacher-facing translation as R2. Finish it when a pilot school's teachers need it; do not list the entire app as English-only.

## Instructions for an implementation agent

1. Treat this as a **gap audit, not an order to build every competitor module**. Confirm the first pilot school's workflow and choose one vertical slice.
2. Re-read the current code and tests before changing anything. Preserve existing data and the user's uncommitted files. Do not copy stale "missing" labels from older market documents.
3. Define the user, permission boundary, data model, screens, migration, audit events and export for the chosen slice. Keep students, guardians and schools isolated.
4. Add tests for the workflow's important failure cases, run the repository quality gate and update the access matrix and docs.
5. Do not claim an official Cambridge, Pearson or IB award from a school-calculated mark. The existing official-results register keeps those sources separate.
